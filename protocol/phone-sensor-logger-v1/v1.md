# phone-sensor-logger protocol, version 1

**Specification version:** 1.0.0 · **Status:** stable · **Machine-readable schemas:** [`v1.schema.json`](v1.schema.json) (upload batch), [`provisioning-v1.schema.json`](provisioning-v1.schema.json) (setup QR code)

This document defines how a phone running phone-sensor-logger uploads sensor data to a server (a "receiver"), and how a phone is set up to talk to that server. Any server that follows it can receive data from the app; the app knows nothing about what the server does with the data.

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT** and **MAY** are used as described in RFC 2119.

## 1. Overview

- The phone collects readings from the sensors the user has switched on.
- Readings are grouped into **batches** and sent with an HTTPS `POST` to the receiver's **endpoint**.
- Dense sensors (light, motion) can be reduced on the phone to **per-minute summaries** to save battery and data.
- Every batch has a unique identity, so it can be retried safely: receivers store it once.

## 2. Transport and authentication

- Batches **MUST** be sent over HTTPS as `POST <endpoint>` with `Content-Type: application/json`, UTF-8.
- The endpoint is a full URL chosen by the receiver (for example `https://example.com/v1/readings`). The protocol does not fix the path.
- Each phone has its own **device token**, sent as `Authorization: Bearer <token>`. Tokens **MUST NOT** be sent in the URL, because URLs are written to server logs.
- Receivers **MUST** accept request bodies of at least 1 MB and arrays of at least 10,000 items. Senders **SHOULD** keep batches well below these limits.

## 3. The batch

```json
{
  "protocol": "phone-sensor-logger/v1",
  "session_id": "3f2a9c1e-7b4d-4e8a-9f10-2c6d8e4b1a57",
  "batch_seq": 0,
  "sent_at": 1794800830000,
  "timezone": "Australia/Brisbane",
  "app": { "name": "phone-sensor-logger", "version": "1.0.0", "platform": "android", "os_version": "14" },
  "readings":  [ { "sensor": "steps_total", "t": 1794800821187, "value": 7 } ],
  "summaries": [ { "sensor": "light_lux", "minute": 1794800820000, "count": 60, "sum": 7210.5, "min": 98.2, "max": 140.1 } ]
}
```

| Field | Required | Meaning |
|---|---|---|
| `protocol` | yes | Always `phone-sensor-logger/v1` for this version. |
| `session_id` | yes | Identifies a logging session. A new session starts every time logging (re)starts. A random UUID is recommended. |
| `batch_seq` | yes | Batch number within the session: 0, 1, 2, … |
| `sent_at` | yes | When the batch was sent, by the phone's clock. Lets receivers detect a wrong clock. |
| `timezone` | yes | The phone's IANA timezone, e.g. `Australia/Brisbane`. Times are always UTC; this tells the receiver what "morning" means for this person. |
| `app` | no | Information about the sending app, for troubleshooting. |
| `readings` | yes | Raw values (section 5). May be empty. |
| `summaries` | yes | Per-minute aggregates (section 6). May be empty. |

A batch with no readings and no summaries is a **heartbeat**: it tells the receiver the phone is alive even when nothing changed.

### 3.1 Timestamps

All timestamps are **integers: milliseconds since 1970-01-01T00:00:00Z (UTC)**. They come from the phone's clock.

### 3.2 Batch identity and retries

- The pair `(session_id, batch_seq)` identifies a batch.
- A sender **MUST NOT** reuse an identity for different content: once created, a batch is immutable and every retry sends exactly the same content.
- Receivers **MUST** treat a batch they have already stored as a success (`"status": "duplicate"`), not an error, and store nothing again.
- Batches **MAY** arrive late and out of order. Receivers **MUST NOT** assume ordering.

## 4. Sensors

| Sensor | Sent as | Fields | Notes |
|---|---|---|---|
| `steps_total` | readings | `value`: integer ≥ 0 | A **running total** of steps. It resets to 0 when a session starts or the phone reboots. Consumers compute steps between readings, treating any decrease as a reset. |
| `light_lux` | readings or summaries | `value`: number ≥ 0 (lux) | Ambient light. |
| `battery` | readings | `level`: 0–1, `charging`: boolean | `charging` is true when charging or full. |
| `screen` | readings | `on`: boolean | Sent when the screen turns on or off. |
| `activity` | readings | `type`: one of `still`, `walking`, `running`, `on_bicycle`, `in_vehicle`, `tilting`, `unknown`; `confidence`: 0–100 (optional) | From the phone's activity recognition. Sent when the activity changes. |
| `motion` | readings or summaries | `value`: number ≥ 0 | Magnitude of acceleration with gravity removed, in m/s². Usually sent as summaries. |
| `location` | readings | `lat`, `lon`: degrees; `accuracy_m`: metres | **Sensitive.** See section 8. |

## 5. Readings

A reading is one value at one moment:

```json
{ "sensor": "battery", "t": 1794800822003, "level": 0.57, "charging": false }
```

`sensor` and `t` are always required; the other fields depend on the sensor (section 4).

## 6. Summaries

A summary aggregates one numeric sensor over one UTC minute:

```json
{ "sensor": "light_lux", "minute": 1794800820000, "count": 60, "sum": 7210.5, "min": 98.2, "max": 140.1 }
```

- `minute` is the start of the minute, so it **MUST** be a multiple of 60,000.
- `count` ≥ 1, and `min` ≤ `max`.
- Summaries carry a **sum, not an average**, so a receiver can merge several summaries for the same minute (average = total sum ÷ total count).
- Of the v1 sensors, only `light_lux` and `motion` may be summarised.

## 7. Compatibility rules

These rules let the protocol grow without breaking anyone.

- Receivers **MUST ignore** fields they don't recognise, at any level.
- Receivers **MUST ignore** readings and summaries for sensors they don't recognise or don't accept, and **SHOULD** report how many they ignored.
- Receivers **MUST reject** (HTTP 422) a batch whose top-level structure is invalid: a wrong `protocol` value, or missing or wrongly typed required fields.
- Receivers **SHOULD tolerate** invalid individual items inside a valid batch by ignoring those items and keeping the rest, so one bad reading doesn't lose a whole batch.
- Senders **MUST** only send batches that are valid against `v1.schema.json`.

**Versioning:** adding optional fields or new sensors is a **minor** change (specification 1.1.0, 1.2.0…; still `phone-sensor-logger/v1`). Anything that would make a valid v1 batch invalid, or change the meaning of an existing field, is a **major** change: a new protocol value (`phone-sensor-logger/v2`), and receivers keep supporting v1 during a transition period.

## 8. Privacy

- Every sensor **MUST** be off until the user switches it on. Location **MUST** show a clear explanation before permission is requested.
- Senders **SHOULD** offer a coarse location option that rounds coordinates to 2 decimal places (about 1 km) and sets `accuracy_m` to at least 1000.
- Receivers **MUST** decide which sensors they accept and **MUST NOT** store others. A receiver that doesn't need location **SHOULD** tell its users to leave it off, and **MUST** discard it if it arrives.

## 9. Responses

### Success: HTTP 200

```json
{ "status": "ok", "stored": 12, "ignored": 1, "dropped": 0 }
```

| Field | Meaning |
|---|---|
| `status` | `ok`, or `duplicate` if the batch was already stored |
| `stored` | Items stored |
| `ignored` | Items not stored because the sensor is unknown or not accepted, or the item was invalid |
| `dropped` | Items not stored because their timestamp was implausible (receivers **MAY** drop readings far older than the rest of their batch, or in the future) |

Receivers **MAY** add other fields.

### Errors

Errors use **Problem Details** (RFC 9457) with `Content-Type: application/problem+json`:

```json
{ "type": "about:blank", "title": "Too Many Requests", "status": 429, "detail": "Slow down: at most 5 batches per second." }
```

| Status | Meaning | What the sender does |
|---|---|---|
| 401 | Missing, unknown or revoked token | Stop uploading and ask the user to set the phone up again |
| 413 | Body too large | Split into smaller batches |
| 422 | Invalid batch | Don't retry this batch (it would fail again); log it as a bug |
| 429 | Too many requests | Retry after the `Retry-After` header's number of seconds |
| 5xx, network error | Temporary problem | Retry (section 10) |

## 10. Retry policy for senders

- Retry after network errors, 429 and 5xx responses; never retry other 4xx responses.
- Wait `Retry-After` seconds when given; otherwise use exponential back-off with random jitter, starting around 30 seconds and capped at 30 minutes.
- Keep unsent batches on the phone until they are accepted (HTTP 200) or rejected with a non-retryable error.
- Retrying is always safe, because batches are immutable and receivers store each identity once (section 3.2).

## 11. Provisioning (QR code setup)

A phone is set up by scanning a QR code containing this JSON (schema: [`provisioning-v1.schema.json`](provisioning-v1.schema.json)), or by typing the same values:

```json
{
  "type": "phone-sensor-logger/provisioning",
  "version": 1,
  "endpoint": "https://example.com/v1/readings",
  "token": "the-device-token",
  "device_name": "Test phone",
  "profile": "activity"
}
```

- `endpoint` **MUST** use HTTPS.
- The QR code contains a token, so it is a **secret**: show it once, and never screenshot, print or store it.
- `profile` is optional: the name of a runtime settings profile the receiver recommends, such as `minimal`, `activity` or `full` (which sensors to switch on, with what settings). The app asks the user to confirm before applying it.
- Future versions may replace the token with a short-lived one-time pairing code.
